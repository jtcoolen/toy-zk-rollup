# Patches to vendored sol-whir-p3

Vendored from <https://github.com/ethereum/sol-whir-p3>. Kept minimal and
additive: every change here is a new function, never a modified one, so an
upstream refresh cannot silently change a value the verifier depends on.

## 1. `transcript/KeccakChallenger.sol`: `sampleByte` / `sampleBytes`

**Why.** The settlement verifier has to reproduce the Fiat-Shamir transcript of a
real p3 WHIR proof. That transcript is not written down anywhere a verifier author
can read — it is p3's control flow — so it is RECORDED from the Rust verifier as a
byte-level absorb/squeeze program and replayed on-chain
(`contracts/test/vectors/whir_transcript_vectors.json`, generated by
`crates/prover/tests/whir_transcript_vectors.rs`).

Replaying a byte-level program needs a byte-level squeeze. The vendored library
only squeezed field elements (`sampleBase`, `sampleBits`), which consume four
bytes at a time and reduce modulo the KoalaBear modulus — so they cannot reproduce
an arbitrary recorded byte.

**What.** Two new internal functions. `sampleByte` reads one byte from the output
block using the same shift `_sampleUint32` already applies, narrowed to a byte,
and decrements `outputIndex` by one instead of four. `sampleBytes` is a loop over
it.

**Byte order.** p3's `HashChallenger::sample` pops from the END of a 32-byte
output buffer, so the first byte a caller gets is `digest[31]`, then
`digest[30]`. The vendored `_sampleUint32` consumes the block from its low end,
and the low byte of a uint32 is the lowest-addressed byte, so both sides agree on
`digest[31]` first. That agreement is not assumed: the replay test fails loudly if
it is wrong, on the first squeezed byte.

**Blast radius.** None for existing behaviour. No existing function was touched,
and `outputIndex`/`outputBlock`/`inputBuffer` are manipulated exactly as
`_sampleUint32` does. Mixing byte-level and field-level sampling on one state is
well-defined because both consume the same cursor.
