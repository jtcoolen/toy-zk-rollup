\section{System overview and actors}
\label{sec:overview}

This section fixes the vocabulary used throughout the specification: the
components that make up the system, the pipeline that carries a value transfer
from a wallet to an on-chain state update, and the actors together with the
trust boundaries that separate them. Everything stated here is what the code
\emph{enforces}; where a source comment states an intent that the code does not
back, a spec delta records the gap.

\subsection{What the system is}

The repository implements a shielded value pool that proves its own state
transitions with hash-based STARKs and settles them on an EVM chain by
replaying the proof under the native \code{keccak256} opcode \src{README.md:3}.
The state the system tracks is two roots: a Poseidon2-Merkleized commitment
tree of note commitments and a nullifier map of spent notes
\src{contracts/src/ShieldedPool.sol:71-77}. A note commitment is a Keccak-256
digest of its contents, the commitment tree is Merkleized with Poseidon2 (the
one granted hash seam), and nullifiers are SHA3-256 over spend material; spend
authorization is a SPHINCS+ signature over a canonical statement encoding
\src{README.md:31-38}. The precise primitives and encodings are given in the
primitives section; here it suffices that no elliptic-curve primitive sits in
the trust path and that the settlement contract never opens the Poseidon2 tree
\src{README.md:3-14}. End to end the demonstration proves: shielded transfers,
one per-transfer STARK each, a block that recursively verifies its children and
folds them into a single statement, and SNARK-free EVM settlement
\src{README.md:29-54}.

\subsection{Pipeline}

The path from a transfer to a settled state update is a four-stage composition.
The hash and transcript used at each stage differ by design, so that the layer
the EVM must replay is Keccak-only \src{.scratch/pq-shielded-rollup/map.md:62-72}.

\begin{enumerate}
\item \textbf{Client transfer proof.} A wallet proves one transfer with a
  multi-matrix AIR (\code{p3-multi-stark}) whose WHIR commitments run over a
  Poseidon2 transcript, with zero-knowledge blinding on
  \src{README.md:39-42}\src{.scratch/pq-shielded-rollup/map.md:109}. Each spend
  proves nullifier non-membership in-circuit and each output append is
  re-derived in-circuit as a Poseidon2 frontier fold, so the post-transition
  roots are exported as public values \src{contracts/src/ShieldedPool.sol:18-37}.
\item \textbf{Block / recursion circuit.} A block circuit verifies $n \ge 1$
  child proofs in-circuit (recursion via the vendored \code{WhirRecursionBackend}),
  chains each transfer's \code{after} roots to the next transfer's \code{before}
  roots, and folds every child's \emph{verified} public statement into one
  256-bit $\code{statementRoot}$ (D-089) using Poseidon2
  \src{README.md:42-45}\src{contracts/src/BlockStatement.sol:18-29}.
\item \textbf{Keccak re-expression and on-chain replay.} The block proof's WHIR
  transcript is re-instantiated under a Keccak-256 configuration and the
  generated Solidity \code{WhirVerifier} replays the entire FRI/WHIR
  verification using only the native \code{keccak256} opcode
  \src{README.md:46-51}\src{contracts/src/verifier/WhirVerifier.sol:9-34}.
\item \textbf{Settlement.} \code{ShieldedPool.applyBlock} verifies the proof,
  checks root and nullifier continuity against its own stored state, and records
  the attested roots and fee \src{contracts/src/ShieldedPool.sol:144-178}.
\end{enumerate}

The block statement carried across stages 2--4 has the fixed layout
$[\, n, (\text{inputs}_i, \text{outputs}_i)_{i<n}, \code{statementRoot},
\code{rootBefore}, \code{rootAfter}, \code{nfRootBefore}, \code{nfRootAfter},
(\code{fee}_i)_{i<n}\,]$, of length $81 + 6n$ base-field limbs independent of how
many nullifiers and outputs each transfer carries
\src{contracts/src/BlockStatement.sol:11-15}\src{contracts/src/BlockStatement.sol:63-72}.

\paragraph{Permissionless settlement.}
\code{applyBlock} is declared \code{external} with no caller restriction: any
account may submit a \code{(statement, proof)} pair, and the function proceeds
on the verifier's boolean alone \src{contracts/src/ShieldedPool.sol:144-145}.
The soundness of the system therefore rests entirely on what that verifier
binds. The adequacy of that gate is examined in \finding{H-01}.

\paragraph{Verifier bound to the proof bundle, not the circuit.}
The injected verifier consumes a single caller-controlled bundle whose three
sections are \code{CONFIG} (the batch framing prefix: seed, degree bits,
preprocessed/verifying-key digest, grind difficulties, and each round's
schedule), \code{PROOF}, and \code{STATEMENT}
\src{contracts/src/verifier/WhirVerifier.sol:13-34}. The \code{CONFIG} section
is read from that bundle as calldata; the contract itself does not pin it, the
source comment only recommending that a deployment pin
$\Hk(\code{configSection})$ \src{contracts/src/verifier/WhirVerifier.sol:21-24}\src{contracts/src/verifier/WhirVerifier.sol:209-231}.
Because the circuit description the verifier replays is taken from the same
bundle a caller supplies, the binding between the on-chain verifier and the
honest block circuit is not established on-chain; this is examined in
\finding{V-01}.

\begin{specdelta}
The security-model prose states that the chain trusts ``the operator set
allowed to call \code{applyBlock}'' \src{README.md:160-162}. The deployed
contract contains no such set: \code{applyBlock} carries no access-control
modifier and no operator mapping, so settlement is permissionless in the code
as written \src{contracts/src/ShieldedPool.sol:144} (cross-reference
\finding{H-01}).
\end{specdelta}
